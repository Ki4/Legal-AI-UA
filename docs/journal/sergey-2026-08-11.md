# 2026-08-11 — the schema, and four things that were quietly wrong

Six PRs, so `docs/CONTRIBUTING.md` does not ask for an entry. Writing one anyway, because
`/session-start` reads this file rather than GitHub, and the lessons below are the kind that a
future session would otherwise re-learn by repeating them.

## What landed

The database went from one table to seven. Catalogue, per-currency prices, the questionnaire field
dictionary, the append-only action log, and assignments. Two ADRs — conversational intake, and
access following assignment rather than role. The console's service list moved off fixtures onto
Postgres. Decisions are recorded in `docs/specs/admin-console.md` §13 and the PR descriptions;
what follows is only what lives in neither.

## Green gates cannot see an absence

ADR-0010 says the audit log "must exist from the first migration that creates a domain table" and
"cannot be backfilled". Four domain tables shipped before it. Nothing failed — lint, typecheck,
migrations applying cleanly, three green verification scripts, none of which can notice a log that
was never written. **A missing log is not an error, it is silence**, which is the same failure
shape spec §9.15 builds the fetcher-safety conditions around, arriving from a direction nobody was
watching.

The concrete cost, found while probing: a lawyer could clear `is_personal_data` on a field,
dropping a declared GDPR retention obligation, with no trace anywhere.

## A verification script is not an adversarial pass

The first catalogue script was 23 scenarios and entirely green. It tested the rules the migration
_said_ it enforced. A separate probe — written to reach forbidden states by another route rather
than to confirm the intended ones — found two holes in ten minutes: a version could take the live
slot without ever being published (and so stayed editable while clients were being served it), and
a published version could walk back to `draft`.

Root cause of both: "live" was defined by `status`, "frozen" by `published_at`, and nothing tied
them together. One thing said twice.

Same session, same shape: ADR-0005 decided in July that `block_assembly` and `full_generation` are
always `lawyer_required`, "enforced on the data model". It had never been implemented. Found by
reading the ADR while answering an unrelated question about who may edit a service — not by any
gate, and not by any test.

## The previous journal's lesson about stacked PRs was wrong

The 2026-08-04 entry concluded that stacking is safe provided the base branch is deleted on merge.
Followed exactly that today with four stacked PRs. GitHub **closes** a dependent PR when its base
branch is deleted rather than retargeting it, so two closed unmerged, and the one whose base still
existed merged into a feature branch instead of `main`.

Nothing was lost: the branch at the top of a stack carries every commit and applies to `main`
cleanly, which is also the recovery. `docs/CONTRIBUTING.md` now says do not stack, and says why.

Worth noting for its own sake: a rule that was followed and then failed belongs in CONTRIBUTING,
not in a journal. A journal records what happened; guidance has to be somewhere people read before
acting.

## Verification scripts must not depend on seed data

Three scripts counted rows across whole tables. They went red the moment `seed.sql` started
creating its own services — asserting how much demo data exists rather than what the schema
enforces. Scoped to their own fixtures now. A check that fails for a defensible reason teaches
people to ignore checks.

## Left open

- The cloud project's migration ledger is unrepaired until
  `supabase/snippets/repair_migration_ledger.sql` is run there. All seven migrations were applied
  by hand, so the CLI believes none of them exist.
- `service_role` holds no DML on public tables — irrelevant today, and the first thing the Edge
  Function gateway will hit.
- `team` and `anatomy` still bypass the `api/` layer, and `team` is now the only feature querying
  Supabase directly.
- Access-control migrations merged without a second reviewer, under the suspension clause added to
  `docs/CONTRIBUTING.md` today. They are listed in their PR descriptions and are owed a review when
  a second developer exists.
- Open questions in `docs/specs/admin-console.md` §14: Q1–Q9, Q14–Q17. Q4 — the detection window
  promised to clients — blocks all of §9 and is the first of them to answer.
