## Orchestrating three agents at once

The first time work was split across parallel subagents rather than done in sequence. Three things
decided whether it worked, and none of them are about the agents.

**The shared file is written before dispatch, by the orchestrator.** All three zones needed keys in
the same two dictionaries. Parallel edits to one file in one checkout overwrite each other, so the
dictionary was written first and every agent was forbidden from touching it — they were handed the
key set and told to report a missing key rather than add one.

The obvious alternative is a worktree each, and it does not work here: a fresh `git worktree` has no
`node_modules`, so an agent in one cannot run a single gate. Isolation that costs the executor its
ability to check its own work is not isolation, it is a handoff.

**Agents run `npx tsc --noEmit` and nothing else.** Three of them racing `pnpm lint` and `pnpm test`
fight over the turbo cache for no benefit; the orchestrator runs the full set once, after merging.

**Their reports are hypotheses.** The verification rule in `docs/CONTRIBUTING.md` does not stop
applying because the claim came from a subagent — it applies more, since the agent wrote the thing
it is reporting on. Every diff was read before being accepted. All three were accurate, which is not
evidence that reading them was unnecessary.

## The zone boundary produced duplication no agent could see

`authErrorKey` — an eighteen-line switch over Supabase auth error codes — was written twice,
identically, in `LoginPage` and `RegisterPage`. Neither agent did anything wrong. The two screens
were handed out as one zone, a shared module would have been a third file outside it, and the brief
said not to create files.

The general shape is worth keeping: **a split into zones creates duplication that is only visible
from where the zones are joined.** Nobody inside a zone can see it, so it is not something to catch
in review of an agent's work — it is the orchestrator's own job at merge time, and it should be
expected rather than rediscovered. It cost one extraction here. On a larger split it is the
mechanism by which parallel work produces a codebase that says the same thing in five places.

## A diagnosis inherited as a fact

The 2026-08-13 entry recorded that `Select` shipped without its both-themes screenshot because the
dev server hung, and named the cause: `apps/console/.env` defining `VITE_SUPABASE_URL` twice. It
added that this "will cost the next session the same hour."

It did. The cause was not that.

The file defines the variable once — the cloud pair below it is commented out. The local sandbox was
running and healthy (`supabase status` up, `auth/v1/health` 200), and the app served and rendered.
What fails is the browser extension's screenshot: script injection times out waiting for
`document_idle` while `document.readyState` is already `complete`. Evaluating script in the page
works, so the pre-sign-in screens were verified that way — `/login` and `/register` render, the
switcher flips the copy, `<html lang>` follows, the choice persists.

The lesson is not about screenshots. **A hypothesis written into the journal is read as a fact by
the next session**, because the journal is where a reader goes to avoid repeating work. The previous
entry wrote a plausible cause in the same voice it used for verified ones. The habit that fixes it
is small: write the observation, and mark the cause as a guess when it is one.

## A gate that is green because nothing runs the thing that would go red

`PracticeAreaRef` changed from one label to one per language, and the compiler carried that change
into both implementations, every consumer and the tests — except one place.

`ServiceQueryRow` in `services.supabase.ts` is hand-written, and `.returns<ServiceQueryRow[]>()` is
an assertion rather than a check. The PostgREST `select()` string beside it is a plain string. Drop
`label_uk` from it and TypeScript stays silent, every test passes, and `labels.uk` is `undefined` in
a browser. Nothing executes that query against Postgres in CI.

The same shape, one layer down: a value added to a Postgres enum by a migration does not break
`shared/vocabulary.ts` unless somebody runs `pnpm db:types` first. The `Record<Enum, TranslationKey>`
is exhaustive against the generated type, and the generated type is only as fresh as the last
generation.

Neither is fixed here. Both are named because this repository keeps meeting the same failure from
new directions, and the direction is always the same one: the gate is green because the thing that
would have gone red never ran.
