# 2026-08-14, third session — the evidence that did not outlive the session

Five PRs merged and one open, so what changed is in their descriptions and in `docs/ROADMAP.md`.
What follows is the part that fits in none of them: how the work went.

The session was a list handed over at the start — merge the open PR, add a DOM environment and a
component test, test the two checkers, close the `approve_user` hole — and it was worked in that
order. Three of the four turned on evidence I produced by hand and did not preserve.

## The rule was in the file, and I broke it anyway

`docs/CONTRIBUTING.md` forbids stacking pull requests and explains why: tried on 2026-08-11,
deleting the base branch **closes** the dependent PR instead of retargeting it. I stacked #38 on
#37 and got exactly that, verbatim from the API — `Cannot change the base branch of a closed pull
request`, and `reopenPullRequest` refused too. Recovery was a rebase onto `main` and a new PR.

The cost was ten minutes. What is worth writing down is not the cost but the shape: the prohibition
was read during `/session-start`, in this session, and it did not surface at the moment the decision
was made. A rule that is read at a briefing and remembered afterwards is indistinguishable from one
that is absent — and the only difference between it and `check:sql` is that the second one executes.

That is the same sentence this repository has now written about copy, about tokens, about the
migration ledger and about verification scripts. It applies to the workflow rules too, and nothing
enforces those.

## The tests I wrote were not the tests I ran

`scripts/check-copy.test.mjs` and `scripts/py-lane.test.mjs` passed all session. After a rebase both
failed with `SyntaxError: Invalid or unexpected token` and zero tests collected — from files that
had not changed.

The cause is `core.autocrlf=true`, the default a Windows Git install sets up, and the absence of a
`.gitattributes`. **Writing a file and checking one out are different code paths**, and all session
I had only ever exercised the first. `node --check` on the same file passes, and the `.ts` tests
beside them were unaffected, which is what made it look like anything other than line endings.

The failure mode is the one this repository keeps meeting from a new angle: CI runs on
`ubuntu-latest`, where the checkout is LF and all 180 tests pass. So the two files added that
morning **to make the gates honest** were themselves green for the machine and red for the person,
and it was found by accident, during a rebase done for an unrelated reason.

Fixed with `* text=auto eol=lf` (#41). The stored blobs were already LF, so the diff is one new
file and nothing else moved — which is also why nobody would have found it by reading.

## The strongest evidence of the session was not preserved

`supabase/snippets/verify_approve_user.sql` has 13 scenarios. The number that matters is a different
one: I pasted the July version of the function inside the same transaction and ran the same
scenarios against the defect. Six went red, including `FAIL 7. an admin demoted themselves and
locked the door behind them` and `FAIL 8. approving a nonexistent user reported success`.

That run is the only thing separating a verification from a restatement of today's code in today's
assertions. The probe file lived in a scratchpad directory and is gone. CI runs half of it — the
scenarios against the fixed function — and there is no way to re-run the half that proves they can
fail.

The same gap covers everything else verified this session. Seven probes against the component test
(collapse two emptinesses, zero the elsewhere count, unwire the retry button, let developer text
through, remove the loading branch, drop the cleanup setup, drop the env block); two against the
script tests (revert `buildCmdLine` to the vulnerable form, drop `aria-label` from the attribute
set). Every one turned exactly the expected test red. Every one is described in a PR. None of them
is a command anybody can run.

A test proves the code does what it says. Nothing here proves the test can still tell. That is the
next level of the same ladder this session spent the day climbing, and the honest name for it is
mutation coverage, which the workspace does not have.

## What went unverified

`docs/specs/console-feature-dod.md` §8 requires the screen **seen rendering, in both themes, with
the browser console clean**. That did not happen once today. The Chrome extension could not inject
into `localhost:5173` — three attempts, then I stopped rather than looping — and I fell back to
checking the same chain through the auth endpoint and PostgREST with `curl`: sign in, read the JWT's
role, read the catalogue and the practice areas as that user. That proves the data path. It says
nothing about the screen.

Worth stating plainly because the new component test makes it easy to confuse: **jsdom applies no
stylesheet.** The test decides which dictionary key each branch renders. It cannot decide whether
the result is legible, whether the dark theme survived, or whether anything overlaps. §8 keeps both
requirements for that reason, and today only one of them was met.
