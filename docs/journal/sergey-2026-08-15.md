# 2026-08-15 — the client half, and three ways of finding out the schema was wrong

Two PRs merged — #50 (ADM-57, entitlements) and #51 (ADM-63, orders, plus ADR-0019) — so what
changed is in their descriptions and in `docs/ROADMAP.md`. What follows is the part that fits in
neither: how the work went.

## The stacked-PR rule was passed rather than tripped over, and partly by luck

`docs/CONTRIBUTING.md` forbids stacking pull requests: tried on 2026-08-11 with four, and deleting
the base branch **closed** the dependent PR unmerged. Today `sergey/orders-table` was branched off
`sergey/entitlements` while the latter was still unmerged, and nothing went wrong — because PR #51
was opened only after #50 had merged. GitHub then showed one commit in it, as it should.

The prohibition is about _open_ stacked PRs, not stacked branches, and the document's own remedy —
"merge the base to `main` first and branch again" — is what happened in effect. Worth recording
anyway: that ordering was chosen because the diff would read better, not because the rule was
recalled at the moment of the decision. The rule was read during `/session-start`, in this session,
and did not surface when it was relevant. That is the same observation the 08-14 journal made about
it, from the other side. It came out right this time; twice is not a mechanism.

## The order of the two tasks was the design decision

The session was asked for ADM-63 and expanded to include ADM-57 on the suggestion that they overlap.
They do, but the useful consequence turned out to be sequencing rather than sharing: building
entitlements first is what let `orders.entitlement_id` be a real foreign key in the first migration,
instead of a nullable column added later to a table that already has rows. The reverse order
produces the same amount of code and a worse schema.

That is also the second dependency row in two days that was wrong and unnoticed. Q21 recorded ADM-57
as blocking ADM-63 on a premise the shipped schema had already dissolved; ADM-57's own row named
ADM-1 where it meant ADM-62. One was imaginary and one was real, and reading could not tell them
apart — both were settled by building the thing and looking at what it needed.

## Two verification scenarios asserted behaviour the platform does not permit

`verify_entitlements.sql` was written expecting a lawyer to be refused `entitlements` with a
permission error, the way `client_identities` refuses everybody. Both scenarios failed, and the
migration was right. An admin has to read those rows, and an admin and a lawyer reach Postgres as
the same database role — `authenticated`, with the distinction living in a JWT claim that a grant
cannot see — so the grant is unavoidable and the refusal is a silent empty result.

Neither reading the migration nor reading the spec surfaced that. Running it did. Written up in §13
of the console spec and generalised in ADR-0019: withholding a grant makes a denial loud only where
the table has no authorised reader inside the same database role. Everywhere else the empty result
is the design, and the answer is that no screen without the right reads the table at all.

## Three probes, and again nothing will run them tomorrow

Each turned exactly one scenario red and nothing else:

- `if false` in place of the ADR-0005 review requirement → scenario 6.
- the coverage question asked of the client instead of the purchase → scenario 10b.
- the reviewer arm dropped from the read policy → scenario 17.

The second is the one worth keeping in view. It is a one-token difference between two functions that
both return true for a covered client, and the only thing separating them is which question is being
asked — is this client entitled to this service, or did _this purchase_ pay for _this document_.
Nothing about the code looks wrong in either form.

They lived in a scratch directory that no longer exists. PR #51 names them, which is where this
repository has now put the same evidence four times. The debt is recorded and is not getting older
quietly.
