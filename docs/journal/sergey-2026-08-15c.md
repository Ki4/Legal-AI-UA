# 2026-08-15 (third sitting) — the norm register

PR #54 carries what changed. This is the part that fits in no PR description: how the work went, and
what was tried and dropped on the way.

Named `c` because the commits are dated 2026-08-15 and two journals already carry that date; the
sitting ran past midnight and the session closed on the 16th.

## What was tried, and what it taught

**The backlog line was read as a zone assignment and worked as a dependency.** §10 says "Fetching,
normalization and diffing belong to the core owner's zone", which is a sentence about ownership.
Read alongside ADR-0004 and ADR-0016 it is also a sentence about _location_: the AI core is Python,
lives in `apps/core`, and is reachable only through the gateway. None of those three exist, so
ADM-41, ADM-42 and ADM-43 were each blocked on ADM-3 and ADM-5 without any row saying so.

Nothing in the documents was wrong. The blockage was in the join between two correct documents, and
it was only visible from inside the work — the question "where does this code go" does not come up
until there is code. That is the second time in a week a dependency turned out to be imaginary
(Q21's was the first, on 2026-08-14), and both times the way it was settled was the same: build the
thing and see what it actually needs.

**A cap can be enforced at the write and still not hold.** The interval guard was written first as a
before-trigger, which is where every other rule in this schema lives, and it looked complete. Then
the verification script needed a scenario where a service is published _after_ the dependency
exists — and that write touches neither `law_norms` nor `service_law_refs`, so no trigger on either
can see it. The answer was to stop enforcing the cap and start deriving it: the stored column keeps
what a lawyer asked for, and `effective_probe_interval()` is what the scheduler is handed. The
trigger stayed anyway, because §4.9 promises the lawyer a refusal at the moment they try, and a rule
that only takes effect silently later is not the same product.

Worth keeping in view: the trigger was not wrong, it was _insufficient in a way that testing found
and reading would not have_. The scenario had to be written before the gap appeared.

**Answering a question can remove a dependency.** Q4 was recorded as "the first question to answer
in this group — the rest depend on it". The answer was that we do not promise a number of days at
all, and the four questions listed under it (Q5–Q8) turned out to depend on nothing Q4 held. The
rule Q4's number was feeding did not disappear either; it changed owner, from a commitment to a
client into an engineering bound we can revise. A question can be load-bearing for a rule and not
for the questions filed beneath it.

**Two verification scenarios were wrong and the schema was right both times.** Scenario 12 demanded
a refusal for an interval of three days when the cap is seven — the code correctly allowed it.
Scenario 13 tried to publish a version of a service with no primary lawyer, which the catalogue
migration has forbidden since 2026-08-11. Same shape as the finding on 2026-08-15's first sitting,
where two scenarios asserted a loud refusal that the design makes silent: the script is the newer
and less-reviewed artifact, so when script and schema disagree the script is the better first
suspect. Neither failure was visible until it ran.

**`allowImportingTsExtensions` belongs to the consumer, not the package.** `packages/law-refs` uses
explicit `.ts` extensions so Deno can read its source unchanged (ADR-0020). Setting the flag in that
package's own tsconfig was not enough: `tsc` applies the _importing_ project's options to files it
follows into, so `apps/console` failed to compile on somebody else's import style. It moved to
`packages/config/tsconfig.base.json` with the reason written beside it.

**The feature was finished, tested and unreachable.** `/law` and `/services/:id/law` were routed,
typed, covered by sixteen and ten component tests, and had no link anywhere in the product. Lint,
typecheck, 392 tests, `check:copy`, `check:sql` and `docs:check` were all green on a screen nobody
could open. It was caught by writing the dictionary key `nav.law` and then noticing nothing used it
— which is luck rather than method. DoD §1 gained a checklist line; no gate can see this, because
"reachable" is a claim about the product rather than about the code.

## What was abandoned, and why

- **A nested PostgREST embed for dependents** — norm → `service_law_refs` → `services`, read back
  through the same table from the other direction. It works, and the select string is a thing nobody
  can verify at a glance six months later. Two flat queries and a join in memory say the same thing
  and are readable.
- **Storing `stale by time` and `scheduled` as `law_norm_state` values.** Both are computable —
  one from `last_verified_at` plus an interval, the other from a signal row that does not exist yet
  — so a column for either would be a copy of the truth that drifts from it.
- **Keeping `no impact` as a resting state**, which §9.11's table lists. Its own definition ends
  "re-fingerprint and continue", after which the fingerprint matches and the norm is `verified`; two
  simultaneously true states is the second answer §6.1 refuses. It became a transition, and the
  judgement survives in `audit_events` with its author — which is what §9.11 was actually asking for
  when it said the decision is recorded rather than treated as housekeeping.
- **Refusing a pasted pinned revision.** §9.2 describes it as a trap, which reads like grounds for
  rejection; §9.5.1 tells the lawyer to paste it anyway. Resolving it and saying so on screen is the
  reading that serves both, and rejecting would have taught lawyers to edit URLs by hand before
  pasting — which is the same trap with an extra step.
- **Putting the cadence editor on the service's law tab**, where §4.9's user story sits. The cadence
  belongs to the norm every dependent service shares; under one service's heading it reads as that
  service's setting, which is the misconception §9.3 exists to prevent. §4.9 is annotated with where
  the story is served instead.
