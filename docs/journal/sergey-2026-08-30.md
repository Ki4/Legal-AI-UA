# 2026-08-30 — three things the spec could not have known, and one I broke myself

The session ran in cycles: close the decisions, build the storage, attack what was built, then go and
read the actual source. Each cycle found something the one before it could not have.

## What attacking my own code found

Eleven defects, four of them in SQL and three in the spec.

**The worst by meaning**: a normalizer bump was indistinguishable from an amendment. Raise
`NORMALIZER_VERSION`, and the next probe of an unchanged article reduces it under new rules and
hashes differently — which is every downstream reader's definition of a drift. Two hundred norms
`drifted` on one morning, each with a one-business-day triage clock. The header of my own migration
claimed keeping the text prevented exactly that morning. Keeping the text is necessary and not
sufficient; a revision now says whose doing it was, and the label is asserted by the fetcher rather
than inferred, because the case where the article changed _and_ the normalizer moved is real and
inferring would hide the half a lawyer must see.

**The worst by consequence**: `grant update` on `law_norms` was table-level, so a lawyer with the
console's own credentials could `PATCH` `last_verified_at`. §9.10 exists to make "no difference
found" and "no check completed" impossible to confuse, and `freshness.ts` computes the badge straight
from that column — so a broken or entirely unbuilt fetcher could be made to render as a quiet week, by
hand. Column-level grants now, and the console was checked to write only two of them.

Two more worth keeping: the adopt trigger updated the register unconditionally, so a revision
inserted out of order would have made it claim the article currently says something it stopped
saying; and `observed_at` defaulted to `now()`, which is transaction time, so two rows written in one
transaction shared a timestamp the ordering depends on.

## What I broke myself

I copied `audit_change` from a migration two weeks old and dropped the `document_blocks` mapping
added since. Every write to that table would have raised `no entity mapping` — a shipped feature
stopping entirely — and the diff that did it reads as a function being added rather than a branch
being removed.

The fix that matters is not the mapping. `check:sql` now requires the last restatement to map every
table carrying an audit trigger, asserted in both halves and confirmed against the real tree by
removing the mapping and watching it fail. The rule is in `supabase/CLAUDE.md` where the next person
copying that function will be standing.

The checker shipped with a bug of its own: a lazy pattern reaching from `create trigger` to the next
`audit_change` walked through unrelated triggers and accused two tables that are not audited. Caught
by running it against the real repository rather than only against its fixtures — kept as a case.

## What the live source changed

Two findings, neither derivable from reading the spec.

**The page our register points at contains no article text.** `/laws/show/2947-14` is a JavaScript
shell. A fetcher built to §9.2's literal instruction would have extracted nothing from every norm on
the platform. §9.15's non-empty invariant would have caught it loudly, which is the condition working
— and it would still have been a day spent, after the schema was built around the assumption.

**That split is a gift.** §9.7 asks for a cheap probe and an expensive comparison, and "cheap" meant
an `ETag` nobody had checked. The shell is 34 KB carrying a redaction date that moves only when the
act is amended; the text is 547 KB behind it. A statement by the publisher about the document beats a
property of an HTTP response.

The fixtures earned their place on the first run: they caught a blank-text assertion measuring the
whole slice, which — since the heading is deliberately part of the returned text — could never see an
empty string. An assertion that cannot fail, in the module written entirely to prevent those.

## What I deliberately did not do

**No invented rada fixtures before going to the site.** A hand-written fixture proves a parser can
read what its author imagined, and ADR-0011 chose to build precisely to remove that ignorance.

**No notification delivery.** §10 defers client-facing notification until `apps/web` and real orders
exist. `decideTriage` returns who is owed what and when — an obligation a channel can later read —
and sends nothing. Overtaking a sequencing decision quietly is not initiative.

**No lower bound on `published_revision_date`.** I nearly added one to catch a mangled year, and it
would have rejected the truth: acts of the Ukrainian SSR are still in force, and `322-08` is from 1971.

## What cost time

Three times, `\r`, `\n` and `\u` inside JS template literals and shell heredocs became real
characters and corrupted probe anchors. After the third I moved every invisible character in the
tests to `String.fromCodePoint`, where a reader can see it.

And I misdiagnosed the test failures. I called them load flakiness when "36 files of 50" pointed at
file-level failure from the start; the cause was `Failed to start forks worker`, and
`--no-file-parallelism` is green and twice as fast. Two unnecessary two-minute runs, and a wrong
statement made to the user before the right one.

## Where it stops

Everything but the network call. The parser, the reduction, the fingerprint, what a probe means, what
a triage decision obliges — all pure, all tested. The edge function that makes requests on a schedule
is not written, and no SQL from this session has ever been executed: Docker was down all session.

Next is ADM-42 — a pasted citation confirmed by its own fetched text. §12 already requires it before
the scheduler, and it catches the one mistake the entry form cannot see today: right shape, wrong
article.
