# 2026-09-01b — the fetcher's first request, and a commit that went to the wrong branch

Tier 3. Read on request. PR #67 documents what changed; this records how the session went, which
has no PR to live in.

## A commit landed on `main` because a branch was created and not stood on

The session opened with `git checkout -b sergey/article-confirmation`, which reported "Switched to
a new branch". Eleven tool calls later the work was committed — and it was committed on `main`.
The branch existed, pointing at the commit `main` had been on when it was created; `HEAD` was
somewhere else.

Nothing noticed for the length of a feature. `git status` was run twice and its first line — `On
branch main` — was not read, because it was being run to see whether the tree was clean. The gates
all passed, because the gates do not care which branch they run on. What finally said so was
`gh pr create`: **"No commits between main and sergey/article-confirmation"**, which is a confusing
sentence until you realise it is literally true.

The recovery was cheap — fast-forward the branch onto the commit, reset `main` to `origin/main` —
and it was cheap only because nothing had been pushed yet. A `git push` before the PR attempt would
have put an unreviewed feature commit on `main` directly.

**What I take from it:** the failure was reading a command's output for the one field I was asking
about. `git status --short` prints no branch line at all, and that is the form I had been using all
session. The habit worth having is checking the branch at the moment of committing rather than
trusting the checkout that happened before the work.

Not proposing a hook for this. A pre-commit branch check would fire on every commit to protect
against a mistake that is visible in `git log --oneline -1` a second later, and the repository
already has more gates than a session can hold in mind.

The middle row is the one worth keeping in view. The tsconfig I wrote used a character class in
`include` — `*/[!.]*.ts` — which tsconfig globs do not support, so the project matched **no files**
and typechecked clean. It was green for the same reason an empty test suite is green. I only looked
because the split into two projects was the point of the exercise and I wanted to see the split;
had I written it as one project I would have shipped a package that nothing compiles.
