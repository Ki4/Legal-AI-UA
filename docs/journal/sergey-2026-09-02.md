# Session — 2026-09-02, credentials for a gate that only reads

Two pull requests merged (#68, #69) and the cloud's migration ledger repaired. What those
descriptions cannot hold is how the second half of the session went, which was almost entirely
about a credential rather than about code.

## Three tokens, and the one command that would have saved two

The gate needs `supabase migration list --linked`. Reasoning from what it does — read a ledger —
the first token was scoped read-only, with `Migrations` at `Read`. CI returned
`LegacyDbConfigLoginRoleStatusError: 403`. The second guess widened `Database Config` and
`Database JIT` to read-write, on the strength of the error's name. Same 403.

`supabase migration list --linked --debug` printed the answer in one line:

    HTTP POST: https://api.supabase.com/v1/projects/{ref}/cli/login-role

The command does not read the migrations endpoint at all. It mints a temporary login role and then
connects to the database directly, which is also why it never needed `SUPABASE_DB_PASSWORD` — the
role replaces the password. A POST to a project-scoped database endpoint needs `Database` at
read-write, and no amount of reasoning about what the gate _conceptually_ does was going to produce
that. **Ask the tool which URL it calls before deciding which permission it needs.**

The cost of guessing is higher here than usual: Supabase tokens say "Access can't be changed after
creation", so every wrong guess is a new token, a new secret write, and a new CI run. Three tokens
exist now; two are dead and were revoked.

## The rehearsal that made three red runs free

The `cloud-ledger` job carries `if: github.event_name != 'pull_request'` — deliberately, since a PR
that adds a migration has correctly not applied it yet. The consequence is that the job's first real
execution would have been on `main`, immediately after merge, which is the one place "main is always
deployable" says it must not fail.

`workflow_dispatch` on the feature branch runs the same job for real: same secrets, same linked
project, no `main`. Three failures cost nothing and were read as logs rather than as an outage. This
is worth making a habit for any job gated off pull requests — the alternative is a gate whose first
execution is production.

## What was abandoned, and why it is written down

The other route to the same green was `SUPABASE_DB_PASSWORD`. The workflow already declares the
variable, `migration list` takes `--password`, and the CLI reads the environment on its own, so it
would have worked with the strictly read-only token.

It was rejected on two counts. The password is not retrievable — the dashboard offers only "Reset
password", warning that it breaks existing connections — so taking this route meant a reset before
knowing it was necessary. And a postgres password in CI is broader than the permission it avoids: it
is full data access, where the token grants one project-scoped capability. The narrower-looking
option was the wider one.

Recorded here so the next session does not start by reaching for it.

## A description that its own branch disproved

#69's body claimed the cloud lacked `law_norm_revisions` and `law_signals` and that `db push` would
close it. A commit later on the same branch established the opposite — the tables were there, the
ledger rows were not — and the body still said the old thing at merge time. It was rewritten before
the squash, so the permanent record says what happened.

A PR description is a claim made at a moment. On a branch that lives longer than a few hours, it
ages like any other document, and nothing checks it.
