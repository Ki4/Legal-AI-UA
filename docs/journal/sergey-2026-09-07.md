# 2026-09-07 — the order that held, and a gate that printed its own fix

Two PRs' worth of work, and both lessons below belong to neither of them: they are about how the
session went rather than about what changed, so they have no PR description to live in.

## The "cloud before merge" order worked exactly as written down

Last session recorded a specific sequencing rule and deliberately called it a merge step rather
than a debt: `check:cloud-ledger` runs on `main` only, so merging a PR whose migration has not been
pushed turns `main` red immediately afterwards. Today that step was carried out — `20260902120000`
went to the cloud first, the ledger agreed at 18 migrations, then #70 merged and the job on `main`
came back green.

Worth being precise about why that worked, because the flattering reading is wrong. The note did
not enforce anything. It worked because somebody read it at the start of the session, in a file
whose whole purpose is to be read at the start of a session. The very same exposure is now open
again: `20260907120000` is in the repository and not in the cloud, and the only thing standing
between that and a red `main` is another reader of another line. Tier 1 is doing real work here,
and it is doing the kind of work that a mechanism would do better.

## A gate that prints the fix costs a minute; one that prints a complaint costs a session

The new SQL function made `packages/db/src/database.types.ts` stale. Docker is not running on this
machine, so `pnpm db:types` — which needs the local stack — could not be run at all, and the honest
options looked like "wait for Docker" or "hand-write the generator's output from memory", which is
guessing at a shape.

Neither was necessary, because the CI step does not merely assert that the file is current: it
regenerates the file and prints `git diff` of the result into the log. The exact eleven lines the
generator produces were sitting in the failure output, and applying them verbatim is not a guess —
it is the generator's own answer, delivered by a different machine. The re-run passed.

The general form is worth keeping: **a failing gate that includes the correction converts a blocked
session into a two-minute edit.** `check-cloud-ledger.mjs` already leans this way, sending the
reader to a specific query rather than prescribing blindly. It is a property worth asking for
deliberately the next time a checker is written, rather than noticing it by luck as happened here.

## What was abandoned, and why it is written down

Two halves of ADM-44 were deliberately not built:

- **The cron.** The cloud holds no edge-function secrets at all, so a schedule pointed at
  `law-sweep` would authenticate against nothing and 401 on every firing. A schedule that fails
  hourly is worse than no schedule: it produces a log full of failures that mean nothing, and the
  day the credential lands nobody trusts the log enough to look.
- **The cheap tier of §9.7.** The act's redaction date is the probe, and `law_norms` has no
  act-level row or column to compare it against. That is a schema decision — where an act lives
  when the tracked unit is an article — and inventing it at the end of a session is how a table
  acquires a shape nobody argued about. §9.8 says scale is not the constraint, so the expensive
  tier alone is correct and merely wasteful, which is the cheapest kind of wrong to be.

Both are debts in STATE with today's date. That is the point of writing them: an absence with a
date reads as a decision, and an absence without one reads as an oversight — and after a few weeks
nobody can tell which it was.
